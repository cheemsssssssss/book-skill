# 交付、分组与分享

## 1. 文件形态

| 场景 | 顶层结构 |
|---|---|
| 单本书源 | 对象 `{...}` |
| 多个书源 | 数组 `[{...},{...}]` |

多数 App 两种都能导入。**批量交付一律用数组**，省得用户逐个导入。

文件名建议：`<站点名>.json`（单个）或 `book-sources-<主题>-<日期>.json`（合集）。

## 2. 必填的元信息

交付前把这三个填好，否则用户拿到手不知道这是什么、还能不能用：

```json
"bookSourceName": "示例站",
"bookSourceGroup": "小说",
"bookSourceComment": "适配 example.com；2026-11-01 验证，搜索/目录/正文正常；正文有广告已清洗；限速 500ms"
```

`bookSourceComment` 建议包含四段：**适配域名 + 验证日期 + 验证范围 + 已知限制**。这是别人（和三个月后的你）判断"要不要修"的唯一线索。

## 3. 分组

`bookSourceGroup` 用 `,` 分隔，常见分类：

- 按内容：`小说`、`出版`、`漫画`、`有声`
- 按状态：`完结`、`连载`
- 按质量：`稳定`、`实验`、`待修`

不要用表情符号和特殊字符，部分版本的导入解析会出问题。

## 4. 版本与维护

书源是**会过期**的资产，站点改版即失效。维护建议：

1. **日期进备注**：`2026-11-01 验证`。没有日期的源，默认当作不可信。
2. **一源一文件**（开发期），交付时再合并成数组。这样改一个源不会影响其他。
3. **保留旧版**：改版时把旧 JSON 留一份在 `archive/`，站点回滚时能救急。
4. **变更记录**：`CHANGELOG.md` 里写「日期 + 站点 + 改了什么字段」，修源时能快速定位上次为什么这么写。

## 5. 分享

- 分享格式就是 JSON 本身，或用 App 的「导出书源」生成分享链接/二维码。
- **分享前清理**：删掉个人 cookie、删掉本地路径、删掉调试用的临时字段。
- 不要在一个源里硬编码别人的账号 cookie —— 会泄露，也会随过期失效。
- 提醒使用者：书源只对公开内容有效，遇到付费章节不要尝试绕过。

## 6. 合规边界（写在交付说明里）

- 书源抓取的是站点公开页面，不破解加密、不绕过登录/付费。
- 高频抓取会给目标站造成负担，`concurrentRate` 不要设得太激进。
- 内容版权归原站/作者，书源只是"阅读方式的适配层"，不改变内容的授权状态。
- 如果站点明确禁止抓取（robots.txt 全站 disallow、页面有明确声明），不要做。

## 7. 交付清单

```
□ validate-booksource.mjs --strict 通过（warning 已逐条解释）
□ 四段链路在 App 里端到端跑通一本完整的书
□ bookSourceComment 写了域名、日期、范围、限制
□ 没有硬编码 cookie / 个人 token / 本地路径
□ concurrentRate 已设
□ 文件名与 bookSourceName 对应
```
